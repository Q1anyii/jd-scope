# 2026-11-25 · JD 识别修正、基底库可编辑、公司档案命名统一

这次是拿真实 JD 验收后的一次集中修正：先修「识别错了」，再补「基底能改」，最后把公司档案的文件名从内部代号改成能直接拿去投的成品名。

## 1. 学历硬条件把「博士」误判成要求

### 现象

某 JD 原文写的是：

> 1. 学历：本科及以上学历
> 2. 专业：计算机类、电子信息类……相关专业
> 3. 年龄：本科毕业生 28 周岁以下，硕士研究生 32 周岁以下，博士研究生 35 周岁以下

旧逻辑输出「博士及以上 / 不满足」，整条岗位被判「不建议投」，必备要求覆盖 0%。

### 根因

`extract_constraints()` 对 **整段 JD 全文** 扫 `DEGREES`，并取最高等级：

```python
for word, level in DEGREES:
    if word in raw and level > best[1]:
        best = (word, level)
```

于是年龄行里的「博士研究生」被当成学历要求，且「本科及以上」反而被「博士」覆盖。
这不是模型问题，是规则抽取的上下文丢失。

### 处置

- 学历只在「学历 / 学位 / 毕业 / 统招 / 全日制 / 本科及以上」这类小句里取；
- 年龄行（含「周岁 / 岁」且没有「学历」）直接跳过；
- 同一句出现多个学历词时取 **最低可接受等级**：`本科及以上，硕士优先` 应该判本科，不是硕士；
- `博士研究生 / 硕士研究生` 先收敛成「博士 / 硕士」，避免「研究生」与「博士」重复计级；
- 没有任何学历小句时 **不生成学历约束**，不再从年龄、公司名等无关文本里猜。

## 2. 学历 / 专业 / 年龄被当成技术能力条目

### 现象

岗位详情的「必备要求」里出现：

- 学历：本科及以上学历 —— 缺失 / 无可比对术语
- 专业：计算机类……相关专业 —— 缺失 / 无可比对术语
- 年龄：本科 28 周岁以下…… —— 缺失 / 无可比对术语

这些行被 `find_terms()` 抽成空数组后，旧 `_req_hit()` 仍然返回 0，和真正的技术缺口一样计入覆盖率分母，直接把必备覆盖率打到 0%。

### 处置

- 新增 `_is_qualification()`：没有技术术语、且属于学历 / 专业 / 年龄 / 毕业 / 证书 / 资格 / 年限门槛的行，不再进入 requirements；
- 同时把「专业」「年龄」抽成真正的硬性条件：
  - `major`：与档案专业做精确/专业大类匹配；不匹配只判「部分」，提示人工确认，不直接判死；
  - `age`：解析成 `{degree, max}` 规则，按档案学历选对应上限；超过只判「部分」，提示核实是否硬性；
- 没有任何可对照术语的普通条目（如「负责与产品经理对齐目标」）保留展示，但 `hit = None`：
  - 不计入 must/duty/nice 的覆盖率分母；
  - 不生成「补课缺口」；
  - 详情里显示「待核对」，不再显示「缺失」。

### 连带修正

- 档案新增「年龄」字段（SQLite v4 迁移，`profile.age`），用于判定 JD 里明写的年龄线；
- 城市约束先把「惠州 - 惠东县」收敛成「惠州」，再和意向城市比对；
- 一条 JD 若只剩资格条件、抽不出任何可对照技术要求，结论改为「待核对」，不再按硬性条件得分直接说「建议投」。

## 3. 基底库只能新增和删除

### 处置

- 后端 `GET /api/bases/<id>` 返回完整正文；`PATCH /api/bases/<id>` 开放
  `code / intent / label / tags / content / active`；
- 改 `content` 时自动重算 `keywords / kind / coverage`；
- `code` 重复会被 SQLite 唯一约束拒绝并返回可读错误，不会静默写坏；
- 前端列表新增「编辑」按钮，弹窗内可改元信息和正文；正文用等宽字体、固定高度、内部滚动；
- 保存后提示新的术语数，并明确「已保存岗位需手动重算才会用新基底」。

## 4. 公司档案文件名不可直接投递

### 现象

公司文件夹里是 `resume.html` / `resume.pdf` / `jd.txt` / `report.md` / `strategy.md`，
投递时还要手动改名；多个公司混在一起时也分不清。

### 新口径

- 成品简历：`姓名-岗位名-简历.html` / `姓名-岗位名-简历.pdf`
- 支撑文件：`公司-岗位名-jd.txt` / `公司-岗位名-report.md` / `公司-岗位名-strategy.md`
- `resume.json` 仍是编辑器事实源，保持固定名，避免编辑器桥接频繁改路径

### 实现

- `companies._prefix()` 生成公司岗位前缀；
- `companies._resume_stem()` 从 `resume.json.meta.name` 或 HTML `<h1>` 取姓名，拼岗位名；
- 编辑器导出 HTML/PDF 时把 `resumeFileName()` 一起传给后端，后端清洗后落盘；
- `_ensure_names()` 做一次性旧文件迁移：
  - 只改名，不覆盖已有成品；
  - 旧 `resume.html / resume.pdf` 改成新姓名版；
  - 旧 `jd.txt / strategy.md / report.md` 加公司岗位前缀；
  - 旧版「岗位名.pdf」如果目录里只有这一份 PDF，也改成新姓名版；
- `read_strategy / jd_text / detail` 统一通过 `_find_support / _find_resume` 查找，新旧命名都能读。

## 6. 已知边界

- 专业匹配是「专业大类 + 关键词」规则，不是教育部的专业目录全量映射；不匹配时只提示人工确认；
- 年龄是提示项，不参与「硬性不满足 → 不建议投」的一票否决；
- JD 结构极不规范时，资格行仍可能漏抽；此时宁可不出约束，也不从无关文本猜；
- 冷门技术词仍不会自动识别，需要继续补 `app/lexicon.py`。
